# 12. Parallel Luau и native code без магии

Срез проверки: **26 сентября 2026**. Это авторская рабочая методика, не полный перевод официальной страницы. Непроверенные в Studio рецепты требуют отдельного запуска.


## Когда распараллеливать
Нужен измеренный CPU hotspot с достаточно независимой работой: выборка данных, расчёт чанков, часть поведения NPC. Если узкое место — GPU, тысячи прозрачных частиц или сетевые запросы, Actor не исправит его. Если каждый worker каждую миллисекунду возвращается в serial, overhead может перекрыть выигрыш.

Script под Actor ещё не доказательство параллельного исполнения. Нужно корректно разделить фазы, проверить thread safety каждого engine member, загрузить modules до parallel-фазы и измерить общий результат, включая передачу данных. Операции записи мирового state выполняются в разрешённой фазе; право read не означает право write.

## Схема работы
Coordinator создаёт ограниченную очередь задач. Worker получает immutable вход, считает результат, прикладывает generation/jobId. Serial commit проверяет, что задача актуальна и получатель жив, затем применяет ограниченный batch изменений. Не передавать весь мир каждому worker и не хранить гигантские дубли таблиц. Для SharedTable отдельно определить владельцев ключей и атомарность операций; «shared» не означает отсутствие логических гонок.

Native code generation использовать для подходящих вычислительных функций после замера. Зафиксировать baseline, warmup, входные данные, расход памяти и ошибки. Не распространять microbench-процент на FPS всей игры. Функция, которая тратит время на engine calls, может почти не выиграть от другой генерации машинного кода.

## Приёмка
Проверять последовательную и параллельную реализации на одинаковых фиксированных входах; результаты должны совпадать в выбранном допуске. Не требовать побитовой детерминированности там, где её не определяли. Данные больших задач, отмена generation, actor teardown и переполнение очереди входят в тесты. До доказанного выигрыша serial fallback остаётся доступным.
