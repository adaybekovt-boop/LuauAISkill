# 46. Асинхронность, отмена и отсутствие скрытых гонок

Авторский синтез; проверка первичных источников 26.09.2026. Не официальный перевод и не отчёт о выполненном Studio-тесте.

## Promise не отменяет причинно-следственные связи
Callback, coroutine, task или promise — разные формы одной проблемы: результат может прийти позже смены состояния. До запуска записать owner и revision. Перед commit проверить, что owner жив, запрос актуален и зависимые объекты не заменены. Затем безопасно применить результат либо выбросить его.

Timeout ожидания не доказывает, что операция не выполнилась. Особенно важно для внешнего сохранения/покупки: после сетевой ошибки durable write мог уже произойти. Повтор без operation ID способен продублировать эффект. Generation token решает stale UI update, но не откатывает совершённую транзакцию.

## Очередь и backpressure
Для сервиса с дорогой работой определить capacity, максимальный возраст задания, concurrency и поведение при переполнении. «Task.spawn на каждый запрос» не является очередью с контролем нагрузки. Под допустимым burst можно принимать ограниченное количество операций, остальные отклонять или объединять по понятной политике.

Coalescing подходит для «последняя запрошенная preview»; он не подходит для потери независимых покупок. FIFO подходит для последовательных изменений одного профиля; глобальная FIFO может необоснованно блокировать всех игроков одной медленной записью. Выбор структуры следует из семантики, а не одного универсального utility.

## Повтор и завершение
Retry классифицирует transient и permanent ошибки, учитывает deadline, jitter и shutdown. Нельзя повторять malformed input до бесконечности. При остановке сначала прекратить новые запросы, затем завершить или отменить допустимую работу, после — очистить callbacks и зависимости. Нельзя destroy общий service раньше consumers, которые ещё пытаются писать.

Тесты строятся с управляемым порядком completion: A→B request, B→A completion; destroy до callback; timeout и поздний success; два concurrent commits; recursive callback during cleanup; повтор вызова destroy. Обычный счастливый сценарий почти не проверяет эту категорию ошибок.
