# 16. Модули, dependency injection и bootstrap

Срез проверки: **26 сентября 2026**. Это авторская рабочая методика, не полный перевод официальной страницы. Непроверенные в Studio рецепты требуют отдельного запуска.


## Дизайн модуля
Каждый сервис имеет узкую ответственность, входные зависимости и lifecycle. Конструктор проверяет конфигурацию, init связывает зависимости, start подписывается, destroy освобождает ресурсы. Не позволять require незаметно запускать бесконечные процессы, менять Lighting или удалять объекты. Инициализация должна быть повторяемой в тестах.

Dependency injection не требует тяжёлого framework. Чистой функции достаточно передать clock, random source, storage adapter или lookup. Это позволяет воспроизвести timeout и ошибку без настоящего сетевого запроса. Интерфейсы указывать рядом с модулем, а не прятать в неиспользуемой документации.

## Границы
Gameplay не должен знать конкретный TextLabel. UI подписывается на публичный read model; persistence получает сериализуемую модель; networking переводит payload в команды; world adapter решает Instance paths. Такая структура помогает менять visuals без изменения authoritative state.

Иерархия зависимостей должна быть ацикличной. Если два сервиса require друг друга, выделить общий контракт или координатор. Не лечить зависание случайным task.wait между require. Точка старта должна объяснять порядок, а сообщения об ошибках — называть сервис и отсутствующую зависимость.

## Изменение существующего проекта
Не вводить новый framework без необходимости. Сначала прочитать действующие conventions, AGENTS.md, tests и manifests. Маленький adapter обычно безопаснее полного rewrite. Разделить перенос файлов, форматирование и функциональную правку, чтобы diff можно было проверить.

Приёмка: повтор bootstrap не создаёт двойной state; сбой одного init даёт понятный отказ; teardown в обратном порядке не обращается к уже уничтоженной зависимости; test doubles не попадают в production tree; shared exports не содержат credentials.
