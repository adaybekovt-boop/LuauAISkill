# A/B-проверка эффекта скилла — 96 заданий

**Все оценки отсутствуют: эксперимент ещё не проводился.** Это авторский evaluation suite, не официальный бенчмарк Roblox и не доказательство прироста.

`prompts-only.jsonl` содержит только задания. `cases.jsonl` — критерии оценщика, critical failures, источники и необходимый уровень доказательств. Не давай эталонные критерии выполняющей модели: убери `evals/` из её рабочей папки. Исключение из поиска само по себе не запрещает чтение файлов. Оценщик получает rubric в отдельном контексте ПОСЛЕ ответа агента.

## Протокол
Зафиксируй точное имя/версию модели, sampling settings, дату, среду Studio, tool permissions, бюджет токенов и времени, commit исходного проекта и целевые устройства. Сравни два режима одной модели: A — без этого пакета; B — с пакетом и одинаковыми остальными возможностями. Для независимости задачи используют свежие контексты и одинаковые исходные проекты. Не сравнивай модель с доступом к Studio и другую без него как чистый эффект документации.

Лучше отделить три эксперимента: (1) закрытая книга против authored core; (2) те же tools, но с полным проверенным официальным корпусом; (3) одинаковый web access, различаются только инструкции skill. Иначе эффект retrieval/tools смешивается с эффектом самой методички. Отдельно записывай объём реально прочитанного контекста, latency и стоимость.

Сделай минимум несколько независимых повторов на выбранных задачах; точное число заранее определяет твой бюджет, а не этот пакет. Перемешай порядок A/B. Слепой оценщик не должен видеть название режима. Ещё лучше добавить реальные новые задачи проекта, которых нет в этом наборе: здесь задания связаны с темами написанной методички и потому не являются нейтральной случайной выборкой всего Roblox.

## Предлагаемая шкала
У каждой задачи три проверяемых критерия. За каждый: 0 — неверно/отсутствует; 1 — частично или только обещано; 2 — корректно и подтверждено необходимыми данными. Максимум 6. Это собственная рубрика, не стандарт платформы. Critical failure обнуляет задачу независимо от красоты ответа. Невыполненный обязательный runtime-тест нельзя оценивать как подтверждённый. Можно отдельно считать качество плана и качество работающего результата, но не смешивать их в один PASS.

Итог публикуй по доменам и уровням доказательств: язык, runtime, сеть, данные, графика, мир, UX, workflow. Сохраняй число задач и повторов, mean/median и разброс, critical failure rate, долю NOT RUN. При малом числе задач не заявляй точный универсальный процент улучшения. Не выдавай стилевое предпочтение одного рецензента за измеримый графический прогресс.

## Графика
Сравни сцены на одних камерах, времени суток, экспозиции, render resolution, quality setting и устройстве. Не меняй число NPC/эффектов между performance runs. Оценка картинки: согласованность материалов/масштаба/света, отсутствие швов и мерцания, читаемость маршрута и угроз, работа слабого tier, доступность настроек. Performance — реальные capture, не вывод по одному screenshot.

## Результаты
`results-template.csv` намеренно содержит только заголовок. Поля score оставлены пустыми. Храни raw ответы, изменённые файлы, stdout/stderr, Studio logs, кадры/профили и точные source paths. В отчёт модели идут только реально выполненные проверки.
