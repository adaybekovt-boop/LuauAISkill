# 03. Типы, unknown и реальные проверки

Срез проверки: **26 сентября 2026**. Это авторская рабочая методика, не полный перевод официальной страницы. Непроверенные в Studio рецепты требуют отдельного запуска.


## Типы помогают разработчику, не защищают remote
Использовать `--!strict` в новом коде. Внутренние структуры типизировать, внешние payload принимать как unknown и сужать проверками. Аннотация `amount: number` не делает данные игрока честными. `value :: Expected` не проверяет структуру и не превращает строку в число.

Для успешного и неуспешного результата удобно объединение `{ok: true, value: T} | {ok: false, error: string}`. Ветка по ok даёт явную модель ошибок. Вместо многосмысленного nil вернуть причину: InvalidRequest, NotReady, RateLimited, NotFound. Не раскрывать клиенту секретные детали внутренней ошибки сервера.

## Порядок валидации данных
Сначала дешёвый type/typeof; потом ограничение размера; далее finite, диапазон, целочисленность, принадлежность допустимому набору; затем права и состояние; в конце дорогие пространственные проверки и commit. Для Vector3 проверить все три компонента до Magnitude. Для таблиц ограничить число ключей и глубину, не выполнять бесконечную рекурсию. Проще принять маленькую явную схему, чем универсальный JSON-подобный payload.

## Типовые ошибки проекта
any размазывается из одного модуля по всему проекту; возврат `nil, error` забывают проверить; широкий `Instance` приводят к Part без IsA; типы UI используются на сервере; пакет API изменился, а старая аннотация сохранилась. Запретить «исправления» массовым `:: any` и отключением strict. Изолированные совместимые адаптеры с комментарием допустимее необъяснённого подавления ошибок.

В тестах обязательно передать NaN, +inf, -inf, пустую строку, ложный bool, таблицу вместо Instance, Instance вне разрешённого контейнера и отсутствующий character. Положительный тест должен подтвердить, что нормальное действие не сломалось после ужесточения фильтра.
